CONTENTO App Testing and Validation Plan

Jeyasri Venkatasubramani Rotation Project

Published

July 8, 2026

The CONTENTO Shiny app was initially created as an internal set of tools for the Lemon Lab and it is now in the process of being released to the public. The app was built to be a user-friendly interface for visualizing results from RNA-seq differential expression analysis and to perform gene set enrichment analysis (GSEA). The main unique feature of the app is its ability to handle multi-contrast datasets, allowing users to compare multiple experimental conditions simultaneously. The app is designed to be used by users with limited programming experience.

1. Rotation Project Goals/Deliverables

CONTENTO is still under development and has not yet been fully tested. The purpose of this rotation project is to perform a comprehensive testing and validation of the app, including installation, vignette validation, and error/warning handling.

The main goals of this rotation project are:

  • Verify installation/download instructions work end-to-end on both Windows and Mac.
  • Validate the SE-object creation vignette and the genome-annotation vignette using real/simulated datasets covering all described examples.
  • Standardize all error/warning handling to the 4-category scheme suggested in the code audit below.
  • Systematically trigger every warning/error condition in the app and confirm the handler behaves as intended. This requires building a test matrix covering all known error/warning handlers and feature-unavailability states, together with representative user input files to trigger them.

The deliverables for this rotation project are:

  • A reusable regression test kit (input files + test matrix + testthat tests) that future contributors can re-run.
  • Code changes to the app to address any issues found during testing, including error/warning handling and vignette updates. This should be done as PR contributions to the main repo, with clear commit messages and references to the relevant test cases.
  • Contribute to the manuscript that describes the app and its features, including a section on the testing and validation process.

3. Installation / Download Testing

  • Follow the published install documentation exactly as a new user would, if possible in both a Windows and a Mac machine.
  • Try every documented installation alternative, not just the primary path.
  • Note any step requiring undocumented manual intervention.
  • Confirm all dependency packages install cleanly. Bioconductor packages (DESeq2, ComplexHeatmap, fgsea, SummarizedExperiment) are the most likely to need special install instructions per OS.
  • Launch the app after each install method and confirm functionality of all sections using testing data sets.

6. Standardize Error/Warning Handling

Dr. Escapa made an initial AI code audit to evaluate if the app is using a consistent error/warning handling scheme. The audit suggested to follow a 4-category scheme for error/warning handling:

Situation Mechanism
1. Can’t proceed until user fixes an upload showModal
2. Reactive/render threw an unexpected error showNotification(type="error") via named handler
3. Reactive computed fine but result is empty/degenerate showNotification(type="warning") via named handler
4. Whole feature/tab is unavailable given current data (annotation, coordinates, MSigDB) inline alert-warning div

The audit also flags candidate issues in the current code; treat its suggestions as a starting hypothesis to verify, not ground truth. The goal is to have a consistent, user-friendly error/warning handling scheme across the app.

The first step is to make an inventory of all the error/warning handling in the app, and identify which of the 4 categories each belongs to and ensure that the handling is consistent with the category. See section 7 for the next step, which is to systematically trigger each.

Based on the pace of the project, Dr. Escapa might start implementing some of these changes so you can focus on the testing and validation work.

7. Systematic Error/Warning Triggering

For every handler identified in the previous step, create a test case that triggers it. Track results in a spreadsheet with informative columns such as:

  • Handler ID (from inventory)
  • Category (1-4)
  • Triggering input combination (e.g. SE file with missing metadata, or MSigDB upload with wrong format)
  • Actual file(s) used to trigger (if applicable). Create a test dataset if needed and store it in inst/test.
  • Expected behavior (e.g. modal appears, notification appears, inline alert appears)
  • Actual behavior
  • Pass/Fail (based on whether actual behavior matches expected)
  • GitHub issue if applicable (if the test fails, create an issue in the repo and link in the spreadsheet)

Example trigger conditions to build test files for (non-exhaustive):

  • SE object missing metadata(se)$contrasts entirely.
  • SE object that is not a SummarizedExperiment
  • Annotation file missing a Geneid column, or with Geneid as a non-character type.
  • Contrast with all-NA stat values, or fewer than 10 unique stat values (GSEA degenerate case).
  • Contrast where all statistics have the same sign (GSEA requires both directions).
  • Annotation column selected for GSEA that yields zero gene sets after filtering.
  • SE with no varpart_* columns (Variance Decomposition tab should not appear).
  • Bacteria-organism SE with annotation lacking start/end/strand (Neighborhood tab inline alert).
  • Fold-change cutoff/FDR cutoff combination that yields zero DEGs for a contrast.

Most of these are just small, hand-built .rds files. You would need to create an R notebook or script to generate them, and store them in inst/test. The goal is to have a complete set of test files that can be used to trigger every error/warning condition in the app.
